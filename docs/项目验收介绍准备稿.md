# TravelByLLM 项目验收介绍准备稿

## 1. 开场 30 秒说辞

老师好，我的项目叫 **TravelByLLM**，是一个基于大语言模型的智能旅游规划系统。

它不是只让 AI 输出一段文本，而是把用户偏好、出发城市、目的地、天数、天气、高德地图点位和历史记录结合起来，生成可保存、可优化、可查看地图、可导出 PDF 的结构化旅行攻略。

技术上，前端使用 **React + Vite + TypeScript + Tailwind CSS**，后端使用 **Node.js + Express + Prisma + SQLite**。AI 生成部分接入 Qwen 模型，同时接入高德地图和天气能力。

## 2. 推荐演示顺序

### 2.1 首页与登录

建议说法：

> 项目有完整的用户体系。用户登录后，可以保存自己的偏好卡片、历史旅行方案和地图收藏地点。

演示动作：

1. 打开首页。
2. 展示登录状态。
3. 可简单展示注册/登录、个人资料、头像或邮箱绑定功能。

### 2.2 偏好卡片

建议说法：

> 为了避免每次重复填写，我设计了偏好卡片。偏好卡片会保存出发城市、旅行风格、交通方式、同行人、旅行天数、天气模式等常用配置。

演示动作：

1. 进入偏好卡片页面。
2. 展示已有偏好卡片或新建偏好卡片。
3. 回到单城市规划页面，选择偏好卡片，说明表单会自动回填。

### 2.3 单城市规划

建议说法：

> 单城市规划适合已经明确目的地的情况。用户输入出发城市、目标城市、天数和补充要求后，系统会生成一份结构化富攻略。

重点介绍：

- 结果不是普通 Markdown 文本，而是结构化攻略。
- 包括总览、每日打法、时间线、交通切换、地点建议、住宿区域建议、天气提示和数据可信度说明。
- 生成后会自动保存到历史记录。

### 2.4 自驾路线规划

建议说法：

> 自驾路线规划更关注城市顺序、闭环路线、驾驶强度、停车补给、路况风险和最后一晚回家。

演示动作：

1. 输入出发城市、途经城市、目的城市和旅行天数。
2. 展示生成结果中的每日自驾节奏。
3. 强调自驾方案会考虑休息、补给、停车和风险提醒。

### 2.5 方案优化

建议说法：

> 方案优化不会覆盖原方案，而是基于历史记录生成一条新的优化版记录。例如可以输入“减少步行”“增加亲子活动”“降低行程强度”等要求。

演示动作：

1. 进入方案优化页面。
2. 从历史记录中选择一个旧方案。
3. 输入优化要求。
4. 展示优化后标题递增，并保存为新的历史记录。

### 2.6 历史记录、地图、天气和导出

建议说法：

> 历史库可以检索、查看详情、继续优化和导出 PDF。地图只显示高德 geocode 成功的已验证点位，不展示假坐标。天气如果不可用或用户选择不参考天气，系统会明确提示，而不是编造天气。

演示动作：

1. 打开历史记录。
2. 查看某条方案详情。
3. 展示天气卡片、已验证地点地图和数据可信度提示。
4. 点击导出 PDF。

## 3. 核心亮点说法

- **结构化 AI 输出**：AI 不是随便写一段攻略，而是输出结构化 JSON，前端按富攻略模块渲染。
- **真实性控制**：没有供应商接口的数据不会当事实展示，例如车次、票价、酒店名、评分、营业状态、门票价格都会过滤或提示核对。
- **三条规划链路统一**：单城市、自驾、方案优化都返回同一套 v3 富攻略结构。
- **地图验证机制**：地点先由 AI 给出文本建议，再由本地服务调用高德 geocode，成功后才显示坐标和 marker。
- **完整业务闭环**：用户登录、偏好卡片、生成方案、历史保存、再次优化、地图查看、PDF 导出，形成完整流程。

## 4. 技术实现问答

### 前后端怎么交互？

可以这样答：

> 前端通过 `/api/plan/city`、`/api/plan/drive`、`/api/plan/optimize` 调后端。后端负责参数校验、读取偏好卡片、调用天气服务、组织 prompt、调用 LLM、解析结构化结果、补全和过滤数据，最后保存到 `TravelRecord`。

### 数据库存了什么？

可以这样答：

> 数据库主要有 `User`、`PreferenceCard`、`TravelRecord`、`FavoritePlace`、`AuthChallenge`。旅行方案的结构化内容保存在 `TravelRecord.structuredContent` 字符串里，所以升级结构时不需要改数据库表结构。

### 怎么防止 AI 胡编？

可以这样答：

> Prompt 中明确禁止编造车次、票价、酒店名等供应商数据；后端解析后还会再清洗；前端展示时也只把 `verified: true` 的地图、地址、天气等作为事实。

### LLM 调用失败怎么办？

可以这样答：

> 后端有 mock fallback 和超时控制。如果模型未配置、超时或返回不可解析 JSON，系统仍会返回可展示的兜底方案，避免页面一直等待。

### 为什么用 SQLite？

可以这样答：

> 这是个人课程项目，SQLite 部署简单，足够支撑用户、偏好卡片、历史记录和收藏地点。同时我使用 Prisma 作为 ORM，后续如果迁移到 MySQL 或 PostgreSQL，改造成本比较低。

## 5. 常见追问与回答

### 这个项目和普通 ChatGPT 问旅游攻略有什么区别？

答：

> 普通聊天只得到文本，我这里做了表单化输入、偏好复用、结构化输出、地图验证、天气参考、历史保存和再次优化，形成了一个可操作的应用系统。

### 项目最大难点是什么？

答：

> 最大难点是把不稳定的 AI 文本变成稳定可渲染的数据结构，并且控制 AI 不编造事实。所以我做了 prompt 约束、JSON 解析、字段补全、数据清洗和 fallback。

### 还有什么不足？

答：

> 目前没有接入真实火车、酒店、门票供应商接口，所以这类价格和实时状态不会展示。后续可以接入正式供应商 API，再把这些字段升级为可验证数据。

### 为什么要做数据可信度提示？

答：

> 旅游规划里很多信息会变化，比如天气、开放时间、票价、路况。如果系统不区分事实和建议，用户容易被误导，所以我把来源和验证状态显式展示出来。

### 怎么测试的？

答：

> 后端有 Vitest 单测，覆盖城市规划、自驾规划、优化方案、天气禁用、LLM fallback、v3 结构补全、供应商字段过滤、高德 geocode 成功/失败等。前端通过 `npm run build` 做类型和构建校验，也做过浏览器冒烟检查。

## 6. 最后收尾说辞

总结一下，这个项目的重点不是单纯调用大模型，而是把大模型能力放进一个完整的旅游规划系统里：用户有账号和偏好，方案能生成、保存、优化、地图展示和导出；同时系统区分“真实验证数据”和“AI 规划建议”，尽量避免 AI 胡编对用户造成误导。

后续如果继续扩展，我会优先接入真实交通、酒店和门票供应商，让攻略从“规划建议”进一步升级成“可预订、可执行”的旅行助手。

## 8. 技术栈选择详细话术

### 8.1 总体架构怎么介绍？

可以这样说：

> 我的项目采用的是比较典型的前后端分离架构。前端负责页面交互、表单输入、地图展示和富攻略渲染；后端负责用户鉴权、数据库读写、调用大模型、接入高德地图和天气 API，并对 AI 输出进行结构化解析和安全过滤。这样设计的好处是职责清晰，前端不会直接暴露敏感密钥，后端也能统一控制数据可信度和业务逻辑。

再补一句：

> 对课程项目来说，这个架构既能体现完整工程能力，也不会过度复杂，方便本地部署和验收演示。

### 8.2 为什么前端选 React？

可以这样说：

> 我选 React 是因为这个项目的前端不是静态页面，而是有比较多状态交互，比如登录态、偏好卡片选择、城市级联选择、AI 生成加载态、历史记录筛选、地图点位展示、PDF 导出等。React 的组件化和状态管理比较适合把这些功能拆成独立模块。

如果老师追问“组件化体现在哪里”，可以答：

> 比如单城市规划、自驾规划、方案优化、历史记录、天气卡片、地图预览、结构化行程展示都拆成了单独组件。这样每个模块职责比较清楚，后续维护或替换也比较方便。

### 8.3 为什么选 Vite？

可以这样说：

> Vite 主要是为了提升开发效率。它启动快、热更新快，适合这种需要频繁调整页面和交互的项目。相比传统打包工具，Vite 在本地开发时反馈更快，课程项目迭代也更舒服。

可以补一句工程化价值：

> 同时 Vite 可以很方便地配置 proxy，把前端的 `/api` 请求转发到后端 `3001` 端口，避免开发阶段跨域和接口地址混乱。

### 8.4 为什么用 TypeScript？

可以这样说：

> TypeScript 是为了提高项目稳定性。这个项目里有很多结构化数据，比如用户信息、偏好卡片、天气快照、旅行方案、地图点位。如果只用 JavaScript，字段变更时很容易漏改。TypeScript 可以提前发现类型不一致的问题。

重点强调刚做的富攻略：

> 尤其是这次富攻略 v3 结构，字段比较多，比如 `overview`、`days`、`timelineItems`、`transportCards`、`verifiedMapPoints`、`dataQualityNotes`。用 TypeScript 可以保证前后端对这些字段的理解更稳定。

### 8.5 为什么用 Tailwind CSS？

可以这样说：

> Tailwind CSS 主要是为了快速做出一致的界面。这个项目页面比较多，如果每个页面都单独写 CSS，样式容易散。Tailwind 可以直接在组件里表达布局、颜色、间距和响应式规则，比较适合中小型项目快速迭代。

如果老师问“会不会太乱”，可以答：

> 我尽量把复杂 UI 拆成组件，让 Tailwind 类名只服务当前组件，不在全局堆很多样式。这样局部修改比较安全。

### 8.6 为什么后端选 Node.js + Express？

可以这样说：

> 后端选 Node.js 和 Express，是因为这个项目主要是 Web API 服务，业务逻辑包括接收表单、查数据库、调用第三方 API、调用 LLM、返回 JSON。Node.js 对这种 I/O 型任务比较合适，Express 也轻量、直观，适合课程项目快速搭建。

再补工程角度：

> 另外前后端都用 TypeScript，技术栈统一，减少了上下文切换。前端和后端可以共享类似的数据结构思路，开发效率更高。

### 8.7 为什么用 Prisma？

可以这样说：

> Prisma 是 ORM，用来管理数据库模型和数据库访问。它的优势是类型安全、查询写法清晰，而且有 migration 机制。比如用户、偏好卡片、旅行记录、收藏地点这些表，都可以在 Prisma schema 里统一定义。

如果老师问“不直接写 SQL 吗”，可以答：

> 直接写 SQL 当然可以，但随着表和关系增多，手写 SQL 更容易出错。Prisma 能把数据库表映射成类型化对象，配合 TypeScript 更容易维护。

### 8.8 为什么用 SQLite？

可以这样说：

> SQLite 的优点是部署简单，不需要单独启动数据库服务，非常适合个人课程项目和本地验收。当前数据量也不大，主要是用户、偏好、历史记录和收藏地点，SQLite 完全够用。

补一句可扩展性：

> 我没有把项目写死在 SQLite 上，而是用了 Prisma。后续如果要部署到线上或多人使用，可以比较平滑地迁移到 MySQL 或 PostgreSQL。

### 8.9 为什么没有直接让前端调用高德和大模型？

可以这样说：

> 主要是安全原因。大模型 API Key、高德 Web 服务 Key、SMTP 授权码这些都不应该放在前端，否则浏览器里能被看到。我的设计是前端只请求后端，后端再去调用第三方服务。

补一句：

> 这样也方便后端统一做限流、错误处理、数据清洗和 fallback，不会让前端直接面对第三方接口的不稳定性。

## 9. API 接入详细话术

### 9.1 可以先用一句话概括 API 流程

可以这样说：

> API 接入分成三层：第一层是前端调用我自己的后端 API；第二层是后端调用大模型、高德地图、天气等外部 API；第三层是后端把外部返回结果清洗、结构化后再返回给前端展示。

### 9.2 规划类 API 怎么走？

可以这样讲：

> 单城市规划走 `/api/plan/city`，自驾路线走 `/api/plan/drive`，方案优化走 `/api/plan/optimize`。前端提交用户输入和 token，后端先验证登录态，再校验参数，然后读取偏好卡片和天气信息，组装 prompt 调用大模型。

后端处理过程可以分 6 步说：

1. 校验用户身份和请求参数。
2. 如果选择了偏好卡片，就从数据库读取偏好配置。
3. 根据城市和日期尝试构建天气快照。
4. 组装 prompt，要求大模型返回 JSON 格式的结构化旅行方案。
5. 后端解析 JSON，补齐缺失字段，过滤不可信事实。
6. 保存到 `TravelRecord`，再把结果返回前端。

### 9.3 大模型 API 怎么接？

可以这样说：

> 大模型部分我通过后端服务统一封装。后端会读取环境变量里的模型地址、模型名和 API Key，然后按 OpenAI compatible 的调用方式发送 messages。项目里还支持配置超时时间和是否开启 thinking 模式。

强调你的控制点：

> 我没有把模型输出直接展示，而是要求它输出一个包含 `markdown` 和 `structuredItinerary` 的 JSON。后端拿到后会先解析，解析失败就 fallback；解析成功也会继续做字段补全和可信度过滤。

如果老师问“为什么要结构化 JSON”，可以答：

> 因为纯文本很难稳定渲染，也很难做地图、天气、导出和后续优化。结构化 JSON 可以让前端明确知道每天有哪些行程、哪些地点、哪些交通切换、哪些是风险提示。

### 9.4 Prompt 设计怎么讲？

可以这样说：

> Prompt 里我重点做了几件事：第一，要求模型只输出 JSON；第二，规定 v3 富攻略结构；第三，明确禁止编造车次、票价、酒店名、评分、营业状态、门票价格；第四，让模型把规划建议标记成 `llm_advice`，不要伪装成实时事实。

再补：

> 这样做的目的，是让 AI 负责“规划推理和表达”，而不是让它冒充供应商数据库。

### 9.5 高德地图 API 怎么接？

可以这样说：

> 高德相关分两类：前端地图展示使用高德 JS API；后端地图和地理编码使用高德 Web 服务。前端只拿公开 JS Key，安全密钥和 Web 服务 Key 放在后端环境变量里。

讲地图验证机制：

> AI 只负责给出地点名称和地址线索，真正的经纬度由后端调用高德 geocode 获取。只有 geocode 成功的地点，才会标记为 `source: amap`、`verified: true`，前端地图才会显示 marker。

如果老师问“geocode 失败怎么办”，可以答：

> 失败就不伪造坐标，只保留文字行程。地图上不会显示这个点，页面会提示暂无已验证地点。这是为了避免给用户错误位置。

### 9.6 天气 API 怎么接？

可以这样说：

> 天气能力也是后端统一处理。后端根据用户选择的城市、日期和天气模式调用高德天气服务，生成一个天气快照 `weatherSnapshot`。这个快照会参与 prompt，也会保存到历史记录里。

强调边界：

> 如果用户选择“不参考天气”，或者天气 key 缺失，或者日期超出可预报范围，系统不会编造天气，而是明确提示天气不可用或需要出行前核对。

### 9.7 历史记录 API 怎么讲？

可以这样说：

> 每次生成方案后，后端都会创建一条 `TravelRecord`。历史记录里保存输入摘要、标题、Markdown 内容、结构化内容、天气信息和天气快照。前端历史库可以按类型和关键词筛选，也可以打开详情继续优化。

重点说明结构化字段：

> `structuredContent` 虽然存在数据库里是字符串，但里面是 JSON。这样后续结构升级比较灵活，比如从 v2 升级到 v3 不需要马上改数据库表。

### 9.8 认证 API 怎么讲？

可以这样说：

> 认证部分使用用户名密码登录，后端验证密码后签发 JWT。前端把 token 存在本地，访问需要登录的接口时带上 token。后端中间件会解析 token，确认用户身份。

如果老师问安全性：

> 密码不会明文存储，而是存哈希。用户修改密码或登录状态失效时，前端会清除 token 并跳回登录页。

### 9.9 邮箱和密码找回怎么讲？

可以这样说：

> 项目里还有邮箱绑定和密码找回能力。后端通过 SMTP 发送验证码或重置链接，相关密钥只存在后端环境变量中。为了避免验证码被明文保存，后端会保存 challenge 记录和哈希信息，并设置过期时间和尝试次数。

### 9.10 PDF 导出怎么讲？

可以这样说：

> PDF 导出是在前端完成的。前端把当前结构化攻略页面渲染区域转成画布，再生成 PDF 文件。这样用户可以把生成的旅行方案保存下来，方便离线查看或提交作业展示。

## 10. 更像“答辩”的完整讲解稿

如果老师让你完整介绍，可以按下面这段讲：

> 我的项目叫 TravelByLLM，是一个智能旅游规划系统。最开始的目标不是简单调用大模型，而是做一个完整的旅游规划应用。用户可以注册登录，维护自己的偏好卡片，比如出发城市、旅行风格、交通方式、同行人和天气模式。生成方案时，可以选择单城市规划，也可以选择多城市自驾路线，还可以从历史记录里选择旧方案继续优化。
>
> 项目的技术栈是前后端分离。前端用 React、Vite、TypeScript 和 Tailwind CSS，主要负责页面交互、表单、地图、天气卡片和富攻略展示。后端用 Node.js、Express、Prisma 和 SQLite，负责用户鉴权、数据库读写、调用大模型、调用高德地图和天气 API，以及对 AI 输出做结构化解析和数据清洗。
>
> 这个项目比较核心的一点是结构化 AI 输出。普通的 AI 旅游攻略往往只是一段文本，不方便保存、优化和地图展示。我这里要求模型返回 JSON，里面包含标题、摘要、每日行程、交通切换、地点建议、住宿区域、补充攻略、地图点和数据可信度说明。前端再根据这些结构化字段渲染成富攻略。
>
> 另外我也考虑了 AI 胡编问题。因为项目目前没有接入真实火车、酒店、门票供应商接口，所以我不允许模型直接生成车次、票价、酒店名、评分、营业状态和门票价格。Prompt 里会明确禁止，后端解析时也会过滤。地图点也不是模型说有坐标就信，而是后端用高德 geocode 验证，成功后才显示在地图上。
>
> 最后，系统还有历史记录和优化闭环。每次生成方案都会保存到 TravelRecord，用户可以回看、导出 PDF，也可以基于旧方案提出新要求生成优化版。这样整个项目从用户输入、AI 生成、数据验证、历史保存到再次优化，形成了一个完整链路。

## 11. 老师深入追问时的稳妥答法

### 如果老师问：你这个项目哪里体现“软件工程”？

答：

> 不只是一个页面调用 AI，而是有比较完整的软件结构：前端组件拆分、后端路由分层、服务层封装、Prisma 数据建模、JWT 鉴权、环境变量管理、第三方 API 代理、单元测试和 fallback 机制。每个模块都有相对清晰的职责。

### 如果老师问：为什么不把所有功能都放前端？

答：

> 因为很多能力涉及密钥和可信数据处理，比如大模型 API Key、高德 Web Key、SMTP 授权码都不能暴露给浏览器。同时 AI 输出解析、过滤、fallback 这些逻辑应该集中在后端，否则前端会变得很重，也不安全。

### 如果老师问：大模型输出不稳定怎么解决？

答：

> 我用了三层处理。第一层是 prompt 约束，让模型必须输出 JSON。第二层是后端解析和补全，如果缺字段会用本地 fallback 补齐。第三层是失败兜底，如果模型超时或 JSON 不可解析，就返回 mock fallback 方案，保证用户界面不崩。

### 如果老师问：你的数据可信度怎么保证？

答：

> 我把数据分成事实和建议。用户输入、高德 geocode 成功、真实天气服务返回的数据可以作为事实；AI 给出的游玩顺序、停留时长、交通衔接属于规划建议。前端会用来源和 verified 状态区分，不把建议伪装成实时事实。

### 如果老师问：为什么要保留 Markdown？

答：

> Markdown 适合完整文本阅读和导出，但结构化 JSON 更适合前端模块化展示。所以我同时保留两种形式：Markdown 作为完整方案文本，structuredContent 作为富攻略和地图展示的数据源。

### 如果老师问：你做了哪些异常处理？

答：

> 包括登录失效跳转、请求参数校验、模型未配置 fallback、模型超时 fallback、JSON 解析失败 fallback、天气不可用提示、高德 geocode 失败不显示假坐标、历史记录为空提示等。

### 如果老师问：如果要上线还缺什么？

答：

> 需要把 SQLite 换成更适合多用户并发的数据库，比如 PostgreSQL；接入更完整的日志监控和限流；接入真实火车、酒店、门票供应商接口；完善权限、安全审计和部署配置。
