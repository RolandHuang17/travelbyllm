# 项目文档综合摘要

## 1. 项目概述

### 1.1 项目名称
基于大语言模型的智能旅游规划系统

### 1.2 项目定位
该项目面向普通旅游用户，目标是构建一个前后端分离的智能旅游规划 Web 系统。用户输入目的地、区域范围、出行天数、预算倾向、出游风格、交通方式、景点偏好、出发城市、同行类型等信息后，系统结合大语言模型能力生成结构化旅游方案，并支持历史记录保存、方案优化、天气参考和分享图导出。

### 1.3 核心目标
- 提供比传统攻略检索更高效的个性化旅游规划体验。
- 通过大语言模型实现区域景点推荐、单城市深度游攻略和多城市自驾路线生成。
- 提供完整的用户使用闭环，包括注册登录、偏好管理、结果生成、历史查看和方案再优化。
- 通过较清晰的系统架构、接口设计和数据库设计，支撑课程项目开发、测试、部署和答辩展示。

### 1.4 面向用户
系统当前主要面向普通用户，不区分管理员角色。用户的典型诉求包括：
- 注册登录并保存自己的偏好与历史记录。
- 配置多张旅游偏好卡片，适配不同出行场景。
- 获取区域景点推荐、单城市深度游方案和多城市自驾路线。
- 查看历史方案并在原有结果基础上继续优化。
- 获取天气参考信息，并将结果导出为分享图。

### 1.5 技术路线总览
- 前端：React + TypeScript + Vite + Tailwind CSS
- 后端：Node.js + Express + TypeScript
- 数据层：Prisma + SQLite
- 外部服务：大语言模型 API、天气接口
- 版本管理与开发：Git、npm、Visual Studio Code

系统整体采用前后端分离架构。前端负责页面渲染、输入采集和结果展示；后端负责参数校验、业务编排、提示词构造、外部服务调用、结果整理和历史记录持久化；数据库负责保存用户、偏好卡片、历史记录和首页景点等核心数据。

## 2. 立项与可行性总结

### 2.1 立项目的与意义
项目选题源于旅游规划场景中普遍存在的信息分散、检索成本高、手动整理耗时长等问题。传统方式通常依赖搜索引擎、社交平台和旅游社区，用户需要自行筛选景点、规划路线、平衡交通与节奏。该项目希望借助大语言模型的文本理解和内容生成能力，把分散信息整合成更清晰、可执行、具有个性化特征的旅游规划结果。

从课程实践角度看，该项目同时具有以下价值：
- 体现大语言模型在生活服务类场景中的应用能力。
- 具备较强实用性和展示效果，适合课程验收与答辩演示。
- 能完整锻炼前端、后端、数据库、接口集成、部署和文档编写能力。
- 在控制开发规模的前提下保留“AI + 实际应用”的创新亮点。

### 2.2 研究内容与建设重点
项目围绕以下几个核心内容展开：
- 构建旅游需求输入模块，支持区域、城市、偏好、天数等参数录入。
- 构建智能方案生成模块，调用大语言模型 API 输出个性化旅游规划结果。
- 构建结构化结果展示模块，支持每日行程、景点推荐、路线概述、天气参考等内容展示。
- 构建历史记录管理模块，实现结果保存、查询、详情查看、标题修改和复用。
- 构建方案优化模块，让用户基于历史记录追加要求重新生成结果。
- 预留分享图导出、地图选区、更多模型支持等后续扩展空间。

### 2.3 技术选型原因
- React + TypeScript + Vite：适合快速搭建现代 Web 前端，组件化程度高，开发体验较好。
- Tailwind CSS：便于快速实现结构清晰的页面布局与统一样式。
- Node.js + Express + TypeScript：适合构建轻量后端服务，便于处理接口、鉴权、业务逻辑与外部 API 调用。
- Prisma + SQLite：适合课程项目体量，建模清晰、开发门槛适中，便于快速完成数据层设计。
- 大语言模型 API：通过调用现成模型能力代替自训练模型，大幅降低实现复杂度。

### 2.4 可行性分析
- 技术可行性高：采用的框架和工具链成熟，资料丰富，生态完善。
- 实现难度适中：核心集中在表单输入、接口通信、结果展示、历史管理和外部 API 集成。
- AI 接入门槛较低：无需训练模型，仅需设计请求参数和提示词即可完成智能生成。
- 项目展示效果好：旅游规划属于贴近生活的直观场景，适合演示。
- 单人开发可操作：通过控制范围和使用成熟技术栈，可在课程周期内完成。

### 2.5 项目特色与创新点
- 聚焦真实旅游规划场景，而非泛化聊天应用。
- 将大语言模型用于旅游推荐、攻略生成和方案优化，突出个性化服务能力。
- 结果采用结构化展示，而非单纯长文本输出，更利于阅读与使用。
- 支持偏好卡片、历史记录和二次优化，增强产品完整性和复用能力。
- 在课程项目尺度内兼顾创新性、实用性和可落地性。

### 2.6 阶段安排
- 第 1 至 2 周：调研、选题、确定技术栈、完成团队组建报告。
- 第 2 至 3 周：完成需求分析，明确功能范围与非功能要求，输出需求规格说明书。
- 第 3 至 4 周：完成总体设计、模块划分、接口设计、数据库设计，输出系统设计说明书。
- 第 4 至 12 周：进行前后端开发、接口联调、AI 能力接入、功能测试和界面优化。
- 第 12 至 14 周：完善系统、整理材料、撰写报告并准备答辩。

## 3. 核心需求总结

### 3.1 业务目标
系统需要解决“普通用户快速获得个性化旅游方案”的问题，核心业务是将用户需求转化为结构化旅游结果，并支持保存、回看和优化。

### 3.2 业务范围
系统包含以下业务范围：
- 用户注册、登录和退出登录。
- 偏好卡片的创建、编辑、删除、查看和切换。
- 首页热门景点图文展示。
- 区域热门景点推荐。
- 单城市深度游攻略生成。
- 多城市自驾路线推荐。
- 历史记录保存、列表查看、详情查看、删除和标题修改。
- 基于原方案的二次优化。
- 结果页天气参考信息展示。
- 旅游方案分享图生成。

系统明确不包含以下范围：
- 酒店预订。
- 餐饮推荐与订座。
- 景点门票价格与库存查询。
- 在线地图导航与精确路径规划。
- 在线支付。
- 多角色权限管理。

### 3.3 核心功能模块

#### 3.3.1 用户注册与登录
用户通过用户名和密码完成注册和登录。系统需要校验字段完整性、密码一致性和账号合法性，并建立登录状态。该模块是偏好卡片、历史记录和个性化服务的基础。

#### 3.3.2 旅游偏好卡片管理
系统支持用户保存多张偏好卡片，用于复用不同出行情境下的默认配置。卡片中包含：
- `cardName`
- `travelStyle`
- `transportMode`
- `driveMode`
- `scenicPreference`
- `departureCity`
- `companionType`
- `travelDays`
- `startDate`
- `weatherMode`

文档中建议单用户卡片数量设置上限，避免冗余；城市字段统一采用地级市粒度。

#### 3.3.3 首页热门景点展示
首页通过预置景点数据展示热门景点图片、名称、地区和简介，用于增强视觉吸引力和提供旅游灵感。该模块承担展示和引导作用，不负责复杂规划逻辑。

#### 3.3.4 区域热门景点推荐
面向尚未明确具体目的地、但已确定区域范围的用户。系统根据一个或多个省份/城市、景点数量以及偏好配置生成景点推荐结果，输出景点名称、所属城市、推荐理由、景点类型及简介。

#### 3.3.5 单城市深度游攻略生成
面向已明确目标城市的用户。系统结合目标城市、出发城市、偏好卡片或临时配置、出游天数等信息生成详细攻略。结果通常包含：
- 攻略标题
- 城市简介
- 每日行程安排
- 推荐景点与理由
- 交通建议
- 天气参考信息
- 注意事项

#### 3.3.6 多城市自驾路线推荐
面向跨城市自驾场景。系统结合区域范围、路线数量、偏好配置和天数生成路线方案。输出通常包括：
- 路线标题
- 路线概述
- 按天安排的城市停留方案
- 主要景点与活动建议
- 城市间大致距离或车程
- 整体出行建议
- 天气参考信息

该功能明确仅适用于自驾场景，不处理实时路况、限行政策和精确导航。

#### 3.3.7 历史记录管理
系统自动保存用户成功生成的旅游结果，并支持列表查看、详情查看、删除、标题修改和作为优化来源再次使用。历史记录应按时间区分，并仅允许当前登录用户查看自己的数据。

#### 3.3.8 方案优化
用户可在历史记录详情页追加新要求，例如“节奏更轻松”“偏向自然风光”“减少城市切换次数”等。系统在原始方案基础上重新组织提示词并生成优化结果，且不覆盖原记录，而是保存为新记录，便于对比。

#### 3.3.9 天气参考信息展示
系统可根据目标城市、路线相关城市和出游日期获取天气信息。天气既可以仅供参考，也可以按偏好设置参与规划决策。天气接口失败时，不应阻断主功能结果展示。

#### 3.3.10 分享图生成
系统支持将结果页核心内容整理为图片版式，供用户保存和分享。分享图侧重展示标题、主要安排、简要天气和系统标识，不要求完整还原全部文本内容。

### 3.4 典型用户流程
- 用户注册或登录后进入首页。
- 用户在个人中心维护偏好卡片。
- 用户进入区域推荐、单城市攻略或多城市路线页面，选择偏好卡片或填写临时参数。
- 前端提交请求，后端校验参数并调用大语言模型与天气服务。
- 后端整理结果并保存为历史记录。
- 前端展示结构化结果，用户可继续查看历史、优化方案或生成分享图。

### 3.5 非功能需求
- 性能：常规页面切换与查询要流畅，大模型请求允许一定等待但应在可接受范围内返回。
- 可用性：页面入口清晰，表单字段通俗，结果结构化展示，历史记录带时间戳。
- 可靠性：用户、偏好、历史数据应可正确保存，异常时能返回清晰提示。
- 可维护性：保持模块化架构，前后端和数据访问层边界清晰，接口命名统一。
- 安全性：密码不能明文存储，敏感密钥只能保存在后端环境变量中，历史记录要按用户隔离。
- 兼容性：优先保证现代浏览器和桌面端体验，接口交互采用标准 JSON。

### 3.6 异常处理要求
系统需要对以下异常进行统一处理：
- 注册或登录输入为空。
- 用户名或密码错误。
- 偏好卡片字段不完整。
- 旅游功能参数缺失或格式不合法。
- 大语言模型接口调用失败。
- 天气接口调用失败。
- 数据库保存失败。
- 历史记录不存在或读取失败。
- 分享图生成失败。
- 其他内部未知错误。

处理原则是返回明确、友好的提示信息，并尽量保证核心旅游规划功能可用；对于天气或分享图等附加能力，应优先采用降级处理。

## 4. 系统设计总结

### 4.1 总体架构
系统采用前后端分离的三层结构，并结合外部服务形成完整闭环：
- 表现层：Web 前端，负责界面展示、表单交互、请求发送和结果渲染。
- 业务层：Node.js + Express 后端，负责校验、业务编排、提示词构造、外部服务调用、结果整理和统一响应。
- 数据层：SQLite + Prisma，负责用户、卡片、历史记录和景点数据的持久化管理。
- 外部服务层：大语言模型 API 和天气接口，分别提供规划生成能力和天气参考能力。

### 4.2 设计原则
- 模块化：按用户管理、偏好卡片、推荐、攻略、历史、优化、天气、分享图等模块拆分职责。
- 前后端分离：前端处理交互，后端处理逻辑和数据。
- 可扩展：预留地图交互、更多模型、更多模板和更复杂推荐策略的扩展空间。
- 可维护：接口命名统一，数据结构清晰，层次边界明确。
- 安全性：密码摘要存储，API 密钥仅保存在后端，数据访问按用户隔离。

### 4.3 前后端职责分工

#### 前端职责
- 展示登录、首页、偏好卡片、推荐结果、历史记录等页面。
- 采集用户输入并进行基础前端校验。
- 通过 HTTP 请求与后端交互。
- 以结构化方式呈现旅游结果。
- 生成分享图并支持下载。

#### 后端职责
- 接收并解析请求参数。
- 进行参数完整性和合法性校验。
- 按不同业务场景组织逻辑。
- 构造适配场景的提示词。
- 调用大语言模型 API 与天气接口。
- 解析并整理返回结果。
- 保存历史记录并返回统一格式响应。

### 4.4 核心模块职责
- `AuthController` / `AuthService`：处理用户注册登录与认证逻辑。
- `CardController` / `CardService`：处理偏好卡片增删改查。
- `RecommendController` 或 `PlanController` / `PlanService`：处理区域推荐、单城市攻略、多城市自驾和方案优化。
- `HistoryController` / `HistoryService`：处理历史记录查询、详情、标题修改等。
- `WeatherService`：封装天气查询逻辑。
- `ShareController` / `ShareService`：处理分享图生成相关逻辑。

系统在设计中采用了实体类、控制类、服务类和数据访问类的分层思想，典型实体包括 `User`、`PreferenceCard`、`TravelRecord`、`ScenicSpot`。

### 4.5 关键业务处理思路
系统关键功能总体都采用“参数整理 + 提示词构造 + 模型调用 + 结果结构化 + 历史保存”的模式：
- 区域景点推荐：根据区域范围、景点数量和偏好生成景点列表。
- 单城市攻略生成：根据目标城市、出发城市和偏好输出每日行程与建议。
- 多城市自驾路线：根据区域范围、路线数量、天数和自驾偏好输出路线方案。
- 方案优化：基于原始记录内容和新增要求重新生成方案。

系统并不依赖传统复杂路径算法或推荐算法，重点在于输入约束、提示词构造、结构化输出和结果持久化。

### 4.6 页面与界面设计重点
文档中对主要页面进行了页面定位、结构组成、界面元素和交互说明设计，重点页面包括：
- 登录/注册页面
- 首页
- 偏好卡片管理页面
- 区域景点推荐页面
- 单城市攻略生成页面
- 多城市自驾路线页面
- 历史记录页面
- 历史记录详情页面

UI 设计强调简洁、清晰、结构化展示和统一风格，尤其重视首页吸引力、表单易用性和结果页可读性。

## 5. 数据与接口总结

### 5.1 核心实体与数据结构

#### 5.1.1 `User`
用于表示系统用户。
- 关键字段：`id`、`username`、`password`、`createdAt`
- 约束：`username` 唯一，密码保存摘要而非明文

#### 5.1.2 `PreferenceCard`
用于保存旅游偏好卡片。
- 关键字段：`id`、`userId`、`cardName`、`travelStyle`、`transportMode`、`driveMode`、`scenicPreference`、`departureCity`、`companionType`、`travelDays`、`startDate`、`weatherMode`、`createdAt`
- 说明：`driveMode` 可为空，仅在自驾场景下使用；`departureCity` 统一为地级市粒度

#### 5.1.3 `TravelRecord`
用于保存历史规划记录。
- 关键字段：`id`、`userId`、`cardId`、`recordType`、`inputSummary`、`resultTitle`、`resultContent`、`weatherInfo`、`createdAt`
- 说明：一条记录可选关联偏好卡片；标题允许后续修改；优化结果作为新记录保存

#### 5.1.4 `ScenicSpot`
用于首页热门景点静态展示。
- 关键字段：`id`、`name`、`city`、`province`、`imageUrl`、`description`

### 5.2 表间关系与约束
- 一个 `User` 可以拥有多张 `PreferenceCard`。
- 一个 `User` 可以拥有多条 `TravelRecord`。
- 一条 `TravelRecord` 可选择性关联一张 `PreferenceCard`。
- `ScenicSpot` 独立存在，主要服务首页展示。

数据库设计中建议：
- 对 `User.username` 设置唯一索引。
- 对 `PreferenceCard.userId`、`TravelRecord.userId`、`TravelRecord.createdAt` 建立索引。
- 通过外键维护用户与卡片、记录之间的关系完整性。

### 5.3 主要接口分组

#### 5.3.1 认证接口
- `POST /api/auth/register`
- `POST /api/auth/login`

用于用户注册与登录，输入主要包括用户名、密码和确认密码，返回注册/登录结果、提示信息及用户基础信息。

#### 5.3.2 偏好卡片接口
- `GET /api/cards`
- `POST /api/cards`
- `PUT /api/cards/:id`
- `DELETE /api/cards/:id`

用于卡片列表查询、创建、更新和删除。创建与更新时主要提交偏好字段集合。

#### 5.3.3 首页与推荐接口
- `GET /api/spots/home`
- `POST /api/recommend/region`

首页接口用于返回展示型热门景点数据；区域推荐接口根据 `regionScope`、`spotCount` 以及 `cardId` 或 `temporaryPreference` 返回景点推荐结果。

#### 5.3.4 规划接口
- `POST /api/plan/city`
- `POST /api/plan/drive`
- `POST /api/plan/optimize`

其中：
- `/api/plan/city` 根据 `targetCity`、`departureCity`、`cardId` 或 `temporaryPreference` 生成单城市攻略。
- `/api/plan/drive` 根据 `regionScope`、`routeCount` 以及偏好配置生成多城市自驾路线。
- `/api/plan/optimize` 根据 `recordId` 和 `optimizationPrompt` 输出优化结果。

#### 5.3.5 历史记录接口
- `GET /api/history`
- `GET /api/history/:id`
- `PUT /api/history/:id/title`

用于查看列表、获取详情以及修改记录标题。

#### 5.3.6 天气与分享图接口
- `GET /api/weather`
- `POST /api/share/image`

天气接口根据 `city`、`startDate`、`days` 返回天气参考；分享图接口根据 `recordId` 或 `resultContent` 生成图片数据或图片地址。

### 5.4 典型输入输出特征
- 输入侧：主要围绕区域、城市、偏好卡片、临时偏好、天数、路线数量、天气模式和优化要求展开。
- 输出侧：强调结构化，包括标题、摘要、按天安排、景点列表、推荐理由、天气信息、注意事项等。
- 响应风格：系统设计文档倾向于统一返回 `code`、`message`、`data` 结构，以便前后端联调和异常处理。

### 5.5 外部服务接入要求
- 大语言模型 API 用于区域推荐、单城市攻略、多城市路线和方案优化。
- 天气接口用于提供目标城市或路线相关城市的天气摘要。
- 外部 API 密钥仅存储在后端。
- 天气接口失败时允许主规划功能继续返回结果。
- 模型输出应尽量贴合系统预设结构，便于解析与展示。
